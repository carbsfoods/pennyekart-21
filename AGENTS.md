# Architecture rules

- Resolve community eligibility on the server from protected user_roles with a legacy-role fallback; approve requests atomically in a super-admin-checked RPC, and synchronize existing administrator role changes so grants cannot diverge.
- Keep community access requests separate from membership invitations; the profile wrapper gates the existing community card and the active admin Communities page hosts the review queue.
- Block community invitations to community creators inside the invite and invite-acceptance database functions, so nobody can be pulled from owning one community into another (checks live in `invite_to_community` / `respond_to_community_invite`).
- Accepting a community invitation requires only a verified account and not belonging to (or owning) another community; the Coordinator/Group Leader/Pro role gate applies to creating or requesting a community, never to joining one through an invite (enforced in `respond_to_community_invite`).

- Share automatic-cancellation classification and partner contact visibility in utilityServices helpers; keep this presentation-only so booking permissions and actions remain unchanged.

- Keep utility reminder pause timestamps scoped to the signed-in seller in a dedicated client hook; suppress only automatic in-app alerts and their floating reminder while leaving Firebase delivery and request actions unchanged.

- Share the presentation-only OrderItemHighlight across normal and utility seller order views; shared customer/delivery dialogs opt in explicitly so seller styling does not alter other roles or order actions.

- Keep delivery Orders card navigation local to DeliveryOrders while preserving quick-filter and notification deep-link entry into All Orders; presentation changes must not alter order actions.
- Keep Stock feature navigation local to DeliveryStock; card navigation must preserve the existing stock search, transfer form, and history filters without changing stock operations.

- Share the global assistant's availability and open command with homepage navigation through `src/lib/chatControls.ts`; the assistant stays mounted at app level so conversations survive page navigation.
- Keep delivery-staff reads and writes of customer address-book locations in an authenticated Edge Function that verifies order assignment, rather than granting staff direct access to other users' addresses.
- Fetch delivery order customer contacts in cached batches through the assignment-checked delivery Edge Function; share the contact display across order lists and notifications to avoid exposing unrelated profiles.
- Use NotificationDialogFrame for admin, seller, delivery, and utility booking alerts; default to blue and opt seller unfinished reminders into orange inside the portal so other roles and order actions stay unchanged.
- Keep utility-service FCM delivery in an authenticated Edge Function that verifies request ownership, resolves the provider server-side, and deduplicates sends so customer clients cannot choose recipients.
- Keep utility booking history reads scoped to the signed-in customer through the existing request ownership policies, so other customers' contact details remain private.
- Share per-user, per-role daily reminder dismissal across delivery, seller, and utility popup flows; keep it client-side and separate from booking/order actions.
- Keep delivery contact-attempt notifications behind an authenticated Edge Function that verifies order assignment, claims the order once, and sends only to that order's customer; customer notice reads must remain scoped to their own order.- Sync e-Life roles into profiles only through the super-admin-checked elife-role-sync Edge Function, matching by normalized mobile and existing role names, so browsers never choose roles from external data.
- Store community role commission rules in app settings and calculate each community's commission from its creator's assigned role to keep reports consistent without a separate rules table.
- Record commission payouts in a dedicated append-only allocation ledger and credit the creator wallet in the same super-admin-checked database transaction, so retries cannot duplicate a payout and customer wallet views remain owner-scoped.
- Keep community creator payouts separate from e-Life area snapshots; recompute role-based profit server-side for India-local date periods, lock each community before rejecting overlapping allocations, and credit the wallet atomically.
- Read e-Life role-to-panchayath allocations only through the super-admin-checked elife-role-allocations Edge Function (read-only, respects the e-Life allowed-tables list); per-person allocation rules (coordinators: one panchayath plus responsible wards; other roles: their allocated panchayath list) live in its allocation.ts, and role-range filtering/ordering lives in src/lib/elifeAllocation.ts.
- Persist commission allocation results as period-keyed snapshots for super admins; load the latest snapshot by default and recalculate/save only when explicitly refreshed.
- Share hierarchy commission through buildHierarchyRows in src/lib/commissionAllocation.ts: coordinator (wards) → team leader (panchayaths) → super admin partner (panchayaths); each role's community share splits equally among same-role holders, and "Super Admin Partner" maps to the super admin rate rule via rateRoleName.
- Edit and delete Add-Admin accounts only through the super-admin-checked manage-admin Edge Function (rules in manage-admin/rules.ts), so login email changes and account removal stay server-side and super admins/self are protected.
- Create WhatsApp account-verification links only through the create-verification-link Edge Function (server-side role check: super admin, team leader, coordinator); redeem through redeem-verification-link with a single-use hashed token, 24-hour expiry, and a current mobile-match check, so browser code can never mint or approve verification.
- Share all WhatsApp-shared link behavior (invite links, referral links, verification links, product share links, Play Store redirect decision, share-message building) through src/lib/appLinks.ts, and build every shared link on its canonical SITE_URL constant — never window.location.origin, which can be the apex domain or a dev host (Android verifies each host separately).
- Route Android deep links through the autoVerify https intent filter in AndroidManifest.xml (only /product, /category, /community, /customer/verify on BOTH www.pennyekart.com and pennyekart.com — never wallet/profile/cart) plus App.addListener("appUrlOpen") with shouldOpenDeepLink dedupe in src/lib/native.ts; WhatsApp previews get per-product OG tags from a vercel.json user-agent rewrite of /product/:id to the product-og function. App Links verification needs the real Play App Signing SHA-256 in public/.well-known/assetlinks.json reachable on both hosts (see PLAY_STORE_CHECKLIST.md), and manifest changes only take effect after the next APK/AAB build.
- Resolve admin-entered links (banners, notification links, offer flash screens) through resolveInternalLink from src/lib/appLinks.ts: internal Pennyekart URLs navigate inside the app with React Router, external URLs keep window.open/target="_blank" — website behaviour for normal browsers is unchanged.
- Keep community role commission rules (fallback percent + per-role rules in app_settings) on a super-admin-only "Commission rules" tab in admin Communities; a BEFORE INSERT/UPDATE trigger on app_settings rejects writes to those two keys by anyone but is_super_admin().
